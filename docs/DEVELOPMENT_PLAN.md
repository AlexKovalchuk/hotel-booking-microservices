# Розвиток Senior Backend / .NET developer через Hotel Booking

Оновлено 2026-10-20. Робочі пріоритети без календарних зобов'язань.
Коригувати за фактичним прогресом, фідбеком співбесід і цілями користувача.
SQL починаємо з основ; використання EF Core не означає знання SQL.

## Обраний напрямок: .NET backend + Azure Developer

2026-10-20 користувач обрав Azure як основну хмарну спеціалізацію.
Йдеться про практичні навички розробки й експлуатації в Azure, а не про
фіксацію конкретного наступного сертифіката. C#/.NET, SQL з основ і EF Core
залишаються фундаментом; Azure поступово застосовуємо до Hotel Booking.
Окремий паралельний AWS-трек наразі не додаємо.

Користувач надав повідомлення рекрутера про вимогу комерційного AWS-досвіду
для Senior .NET і опис Ciklum .NET Engineer. Аналізуємо саме надані тексти,
без перевірки активності вакансії. В описі вказано мінімум 2 роки досвіду,
novice-рівень технологій та AWS-сервіси. Не встановлено, чи це та сама роль,
про яку рекрутер написав як про Senior.

- Azure DevOps Pipelines у цьому описі — CI/CD для AWS-проєкту;
  він не робить вакансію Azure developer-роллю.
- AWS Certified Developer – Associate протягом 6 місяців від початку роботи —
  вимога цієї вакансії, а не причина додавати AWS-сертифікацію до нашого плану.
- Спільні корисні вимоги: автоматизоване розгортання, Docker, IAM/права,
  секрети, моніторинг, самостійність, ескалація проблем та англійська.
  Їх опрацьовуємо у відповідних сценаріях Azure й поточній роботі над backend.
- Розрізняти знання сервісів, власноруч розгорнутий навчальний проєкт,
  сертифікат і комерційний досвід. Відмова через AWS у резюме не є оцінкою
  загального рівня .NET і не доводить перевагу однієї хмари на всьому ринку.
- Коли з'явиться перевірена Azure-практика, описувати в резюме конкретно:
  що розгорнуто, як працює pipeline, доступ до секретів, моніторинг і
  діагностика; позначати Hotel Booking як навчальний/pet-проєкт.

Назва Software Engineer сама по собі не означає нижчих вимог.
Третій опис .NET + Azure вимагає 7 років у cloud, .NET/API/microservices і БД,
а також участі в архітектурі та менторстві. Це заявлені вимоги конкретних
вакансій, а не універсальне визначення Senior.

- Спільна основа: .NET/API, бази даних, продуктивність, інтеграції,
  якість коду, командна робота та відповідальність за життєвий цикл системи.
- Banking: особливий акцент на складному SQL, схемах даних, Oracle PL/SQL,
  документації, англійській, знанні frontend і досвіді Capital Markets.
- Azure: практична робота з Web Apps, Functions, Logic Apps, Azure SQL,
  Cosmos DB, Azure DevOps pipelines, безпекою, IaC, моніторингом та алертами;
  архітектурні рішення й допомога молодшим розробникам.
- Переліки AI, Big Data, NoSQL, Kubernetes та інструментів описують широкий
  контекст роботи. Не вважати кожну згадку однаково глибокою вимогою.

## Основні пріоритети та практика

Наведені нижче приклади — наша інтерпретація практики для Hotel Booking.
Outbox, ідемпотентність, конкретні тести та метрики не були прямо названі
у вакансіях. Це способи опрацювати заявлені теми надійності та якості.

### 1. SQL + EF Core — найближчий пріоритет

- Почати з SELECT, WHERE, ORDER BY, JOIN, GROUP BY, агрегатів і змін даних.
- Пов'язувати LINQ з SQL: фільтрація у БД чи в пам'яті, проєкції,
  пагінація, tracking, Include, кількість запитів і N+1.
- Далі: ключі й обмеження, індекси, execution plans, транзакції,
  рівні ізоляції та конкурентні зміни; складніші запити, CTE й віконні функції.
- Практика: пошук готелів із фільтрами, вибірка номерів, згодом звіти
  бронювань і коректність одночасного бронювання одного номера.
- Критерій: самостійно написати й пояснити SQL, подивитися SQL від EF,
  обґрунтувати індекс та перевірити зміну продуктивності на вимірюваннях.
- Stored procedures вивчити на одному обґрунтованому прикладі. Oracle PL/SQL
  залишити спеціалізацією під конкретний Banking-проєкт після основ SQL.

### 2. C#/.NET, тести та code review — у поточних задачах

- Зберегти роботу над прогалинами зі співбесід, async/await,
  CancellationToken, валідацією, обробкою помилок та авторизацією.
- Додати змістовні unit та integration tests: бізнес-правила, доступ
  власника, робота з реальною реляційною БД у тестовому середовищі,
  помилки й некоректні відповіді Hotels API у Search.
- Опрацювати тестування HttpClient через HttpMessageHandler.
- Практикувати TDD на невеликих правилах, BDD — через зрозумілі сценарії.
  Покриття оцінювати разом із перевіреними ризиками, без гонитви за відсотком.
- Критерій: знайти проблему на review, пояснити наслідки й запропонувати
  виправлення; тест має виявляти конкретну регресію.

### 3. Архітектура та надійність — у міру розвитку інтеграцій

- На Search → Hotels розібрати HTTP-контракти, тайм-аути, скасування,
  обмежені повторні спроби та помилки залежностей.
- На майбутніх Booking/Payment — транзакційні межі, ідемпотентність,
  повторні повідомлення, eventual consistency; outbox за реальної потреби.
- Порівнювати синхронну й асинхронну взаємодію, обґрунтовувати межі сервісів.
- Критерій: пояснити, що станеться при збої чи повторі запиту, і показати
  перевірку поведінки. Не додавати брокер або сервіс лише заради технології.

### 4. Azure та експлуатація — після достатньої локальної основи

- AZ-900 залишається поточною навчальною ціллю; наступні іспити обирати
  після практики й перевірки їхньої актуальності.
- Поступово розгорнути робочий сценарій: App Service/Web App + Azure SQL,
  конфігурація, Key Vault, Managed Identity та мінімальні права доступу.
- CI/CD: build → tests → deployment, міграції БД, перевірка здоров'я,
  відновлення після невдалого розгортання. Azure DevOps — цільова практика
  під вакансію; не дублювати наявні pipeline без навчальної потреби.
- Спостережуваність: структуровані логи, correlation ID, трасування,
  Application Insights, метрики затримки/помилок і осмислені алерти.
- Вимірювати продуктивність коду й SQL до/після змін; розуміти вплив
  масштабування на стан, з'єднання з БД та вартість.
- Згодом описати інфраструктуру одним IaC-інструментом, наприклад Terraform.
  Functions/Service Bus вводити для конкретних фонових чи подієвих задач.
- Критерій: відтворюване розгортання та діагностика збою за телеметрією.

### 5. Інженерна комунікація — разом із реалізацією

- Документувати API, важливі рішення та компроміси короткими ADR;
  підтримувати інструкцію запуску й діагностики типового збою.
- Тренувати пояснення задачі, архітектури, проблеми й виправлення англійською.
- Практикувати зрозуміле review і пояснення рішень іншій людині;
  досвід менторства оцінювати за реальною практикою.
- Критерій: інша людина може запустити сценарій і зрозуміти рішення
  за документацією та поясненням.

## Додаткові напрямки — за цільовою роллю та потребою

- Capital Markets: окреме доменне навчання, якщо користувач обере Banking.
  Технічні сценарії бронювання/оплати корисні для практики коректності даних,
  але не замінюють досвіду Investment Banking або Capital Markets.
- NoSQL/Cosmos DB: спочатку модель даних, патерни доступу й компроміси
  відносно SQL. Практику додавати за обґрунтованого сценарію.
- Docker поглиблювати для запуску й розгортання; Kubernetes — після основ
  контейнерів та експлуатації, коли з'явиться відповідна мета.
- React/Angular: API-інтеграція, автентифікація, CORS, стан запитів і помилки.
  Якщо потрібна практика frontend, обрати один фреймворк.
- Logic Apps, Oracle PL/SQL, ARM, Ansible, Jenkins, Bitbucket та Big Data
  не утворюють окремих паралельних обов'язкових треків.
- AI: поки орієнтація в можливостях і обмеженнях; у текстах немає
  конкретної задачі чи стеку, що виправдовували б новий великий трек.

## Межі оцінки готовності

Комерційний стаж, Capital Markets, освіта, рівень англійської та досвід
менторства користувача не встановлені цими матеріалами. Не робити висновку
про відповідність вакансіям без уточнення. Навчальний проєкт демонструє
навички, але не підміняє заявлені роботодавцем роки production-досвіду.
